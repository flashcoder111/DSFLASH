DeepSeek · API

搜索、OCR、TTS 过去意味着三家供应商，在 deepseek-flash 上它们是三个参数。

By Cameron Voss · 2026 年 11 月 20 日 · 阅读约 6 分钟

TL;DR

  • V4.1-Flash，也就是调用时的 deepseek-flash，在 Messages、Responses 和 Chat Completions 上都支持工具参数。
  • 联网搜索、深度思考搜索、文件输入、链接阅读和安全校验都在服务端完成，调用方只发一次请求。
  • Search、Fetch、OCR、ASR、TTS 另外提供独立接口，适合已经有自己编排链路的团队。
  • 计费是 token 费用加每次工具调用的费用，需要盯住的变量是搜索深度。
  • 官方放出了一个轻量开源客户端，可以直接跑通整套流程。

DeepSeek 的聊天产品一直不只是回答问题。它会搜网页、打开链接、读取上传的文档、听懂语音，还会过滤有风险的回复。以前想在自己的产品里做出同样的效果，得把好几家服务接在一起，再自己写好中间的传参和状态管理。这部分工作现在挪进了模型调用里。

V4.1-Flash 在调用时使用的模型名是 deepseek-flash。它在 Messages、Responses 和 Chat Completions 三个接口上都支持一组可选工具。打开参数，DeepSeek 会执行工具、把结果拼进上下文，最后返回答案。你发一次请求，收一次响应。

一次请求里的五种能力

标准接口上新增了五项能力：

  • 联网搜索。普通模式下开启 deepseek_web_search，模型会判断当前问题是否需要外部信息，自动发起网页或图片搜索，并在答案里附上引用。
  • 深度思考搜索。同一个开关，在思考模式里使用。搜索发生在推理过程中，模型可以在多步推理之间读结果、改查询，而不是只搜一次就下结论。
  • 文件输入。支持 PDF、Office 文档和图片。可以只提取纯文本，也可以按版面解析图文混排的内容，再放进上下文。
  • 阅读链接。打开 deepseek_read_url 后，用户消息里的链接会被自动抓取，网页内容作为回答依据。
  • 安全校验。开启后服务端会审核输入和输出，命中风险规则时返回拒答标识。

这些步骤之间的循环不需要你来管。工具怎么选、调用怎么发、上下文怎么拼，都在 DeepSeek 那边完成。自己做检索链路时常见的一类问题因此消失了：中间环节超时导致工具结果丢失、跳转过程中丢了状态、队列把上下文顺序打乱。

代价是可观测性变弱。你拿到的是答案，不是每一次查询的完整记录。实际做法是把发送的参数和返回的引用都记下来，中间过程当作一个由平台维护的黑盒，错误处理也按这个前提来设计。

两种搜索行为，一个参数

普通模式下的搜索更像一次查询。模型发现信息不够，发一次请求，然后带着引用写答案。产品介绍、时事问题、有明确事实答案的场景，用这个模式就够了。

思考模式下的搜索是推理的一部分。模型可以先做宽泛的搜索，读完结果再收紧下一次查询。做资料梳理时，这种方式比单次搜索覆盖得更全，代价是工具调用次数更多，出第一个字的时间也更晚。

所以这里要考虑流式输出。一个思考模式的回答如果先花六秒去查资料，在不能流式的客户端里看起来就像卡住了。要么把进度显示出来，要么至少给一个正在输入的提示，同时为单轮设置步数上限。

已经自己编排的团队，可以直接调独立接口

同样的底层能力也拆成了单独的 Search、Fetch、OCR、ASR 和 TTS 接口。这对两类团队有用。已经有一套 agent 框架和工具路由的，直接调 Search 和 Fetch，执行顺序仍然由自己控制。做语音产品的，OCR、ASR、TTS 正好覆盖了过去通常要找三家供应商才能凑齐的部分。如果你在犹豫要不要保留现有的 OCR 或 TTS 合同，我们定价页里写清了每个档位包含的额度，对比起来更具体。

有一个能直接跑的客户端

DeepSeek 放出了一个轻量前端 Demo，用的是新接口，还能导入已有的对话记录。托管版和源码都在 GitHub 的 deepseek-ai 组织下，仓库名是 chat-demo。

建议在设计自己的客户端之前先读一遍。它展示了每种能力的请求写法，也给出了界面和服务端之间一个可用的分工方式。真正有价值的是那些不起眼的部分：上传怎么传、引用怎么渲染、拒答怎么展示才不至于让用户困惑。

账单是怎么算出来的

Token 计费和原来一样。使用工具会额外产生一层费用，按调用次数收取。上下文里能答完的对话，成本就是 token 的计算。需要查资料的对话，除了 token，还要为打开的每一个页面付费。

费用项什么时候产生容易涨的地方
输入 token 提示词、对话历史、解析后的文件文本、抓取的网页 长文档和多轮对话
输出 token 推理过程和最终答案 难题上的思考模式
工具调用 每一次搜索、抓取、OCR、ASR 或 TTS 调用 反复查资料的 agent 循环

监控指标里要加上工具调用次数，只看 token 消耗会漏掉很大一块。最容易超出预期的变量是搜索深度：思考模式下问一个宽泛的问题，模型可能在动笔之前就跑了好几次付费查询。抓过的页面做缓存，同一页取两次就付两次钱。给每轮对话设一个步数预算，到了就记录一条日志。定预算之前，当前 V4.1 Flash 和 V4 Pro 的订阅方案与使用额度在我们定价页上有完整对比。

上线前要确认的几件事

  • 面向公众的应用要打开安全参数。它提供的是基础过滤，不等于一套完整的合规方案。内容审核、大模型登记和 AI 标识这些义务，在适用范围内仍然由你来承担。
  • 分阶段测延迟。搜索和文件解析会推迟出第一个字的时间，这种延迟对用户感受的影响，比在榜单上少几分要明显得多。
  • 用用户真正会上传的文档做测试。扫描件、表格和双栏 PDF 是最容易悄悄出错的地方。
  • 工具失败要有兜底。搜索没有返回结果，不应该变成一个空白回答。

对做产品的人意味着什么

从想法到能用的助手，中间的路短了。以前想要搜索加文档阅读，得找三家供应商，再写一层队列把它们串起来。现在这件事是一个参数，省下来的精力会转移到更高一层：界面、权限、数据留存，以及那些真正属于你自己产品的部分。

它不会替你做产品判断。什么时候该搜、什么时候该读文件、什么时候该承认答案不在上下文里，这些仍然是设计工作。API 把围绕这些判断的管道拆掉了，判断本身还是得自己下。
